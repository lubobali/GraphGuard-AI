# Fit a real lakehouse into one gigabyte

GraphGuard can build a small but real lakehouse on this box, and almost all of it costs zero resident RAM. The shape that matches Databricks and Snowflake in late 2026 is **Apache Iceberg tables behind an Iceberg REST catalog**. Snowflake, Databricks, AWS, Google and every open catalog speak that protocol. The best build here is: Iceberg v2 tables in bronze/silver/gold namespaces, files in GraphGuard's own AWS S3 bucket, **Lakekeeper** (a small Rust program) as the REST catalog with its database inside the Postgres GraphGuard already runs, and **Polars + DuckDB + PyIceberg** as engines that run as jobs, not servers. Spark comes later as a start-run-stop batch job. The only new always-on service is the catalog, estimated at tens of MB. Nobody has published a measured number for it, so it gets measured on the box before it stays, the same way Ray was. Be honest about hiring value: Iceberg appears in **10 of 139** (7%) data-platform and ML postings sampled in November 2026, and in **0 of 79** ML-engineer and ML-platform postings. So the lakehouse earns hiring value through what it proves (reproducible training data, point-in-time correctness, data contracts, lineage, access control). The keyword itself buys little. It is still worth building because the owner wants to learn it, and because it fixes a real gap: Redis holds 512,707 feature hashes with no persistence, and those features exist nowhere else.

## Iceberg plus a REST catalog is the shape every big platform speaks

**The table format question is settled.** Iceberg spec v3 went GA on Databricks Unity Catalog in May 2026 ([Databricks docs](https://docs.databricks.com/aws/en/iceberg/iceberg-v3)). Snowflake previewed v3 in March 2026 ([Snowflake release note](https://docs.snowflake.com/en/release-notes/2026/other/2026-03-04-iceberg-v3-support-preview)). AWS S3 Tables expose an Iceberg REST endpoint ([AWS docs](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-tables-integrating-open-source.html)). Snowflake's Horizon catalog is "built on the foundation of Apache Polaris" ([Snowflake blog](https://www.snowflake.com/en/blog/bidirectional-interoperability-snowflake-horizon-databricks/)). Delta Lake is still very active (4.4.1, October 2026), but its cross-engine story is "Delta that also writes Iceberg metadata" (UniForm) ([delta.io](https://delta.io/blog/2026-06-22-delta-4-3-release)). Databricks' own position comes down to "Delta inside, Iceberg REST outside". Hudi is alive but not where platform interop happens. **Write v2 tables, not v3.** Polars, PyIceberg and Trino do not support v3 features (deletion vectors, variant, row lineage) evenly yet, and Trino was reported not v3-ready as of June 2026 ([Atlan](https://atlan.com/know/snowflake/apache-iceberg-v3/)).

**The catalog is the part that makes it a lakehouse.** It does the atomic commit: a compare-and-swap of the "current metadata" pointer. Iceberg's docs say no rename, no consistent listing and no conditional writes are needed from the object store ([Iceberg reliability](https://iceberg.apache.org/docs/latest/reliability/)). All six open catalogs are Apache-2.0 and released within weeks of this report. They differ most in weight. Compressed images measured from Docker Hub: **Lakekeeper ~67MB, Polaris ~417MB, Gravitino ~535MB, Unity Catalog OSS ~2.76GB** ([Docker Hub](https://hub.docker.com/r/vakamo/lakekeeper)). The Unity Catalog image alone would use over 10% of the 25GB disk budget. Lakekeeper is the only non-JVM option. Its open-source build ships OpenFGA permissions, a Grants API, S3 STS credential vending, remote signing, and an option to keep its tables in a non-public Postgres schema ([Lakekeeper release notes](https://docs.lakekeeper.io/about/release-notes/)). That last option lets it live inside GraphGuard's existing MLflow Postgres as a separate database. Polaris is the bigger name and closer to what Snowflake actually runs. It graduated to an Apache top-level project in February 2026, and its heap can be capped with `-Xmx` ([Polaris config](https://polaris.apache.org/releases/1.7.0/configuration/configuring-polaris/)). But it is a JVM service. **No source publishes a measured idle RAM figure for any of these catalogs.** My estimate is that Lakekeeper idles at tens of MB and a heap-capped Polaris at a few hundred MB. Both numbers are inference until measured.

**The current plan (PyIceberg + SQLite catalog) is a fine first step but a dead end.** PyIceberg's own docs warn that SQLite "is not built for concurrency, you should use this catalog for exploratory or development purposes" ([PyIceberg docs](https://github.com/apache/iceberg-python/blob/main/mkdocs/docs/configuration.md)). DuckDB can write Iceberg only through an attached REST catalog ([DuckDB 2.0 docs](https://duckdb.org/docs/2.0/core_extensions/iceberg/writing_to_iceberg.html)). So a SQL catalog blocks DuckDB writes, and it has no permissions and no credential vending. The cheap upgrade path is SQLite → PyIceberg SQL catalog on Postgres (same API, zero new services) → Lakekeeper REST. Every engine connects with `type: rest`, so a later move to Polaris is a config change, not a rewrite.

**Security is the catalog's weak spot, and the pattern repeats.** Polaris had four critical CVEs in May 2026, all about credential vending and location checks, fixed in 1.4.1 ([vulert CVE-2026-42809](https://vulert.com/vuln-db/CVE-2026-42809); [ZeroPath](https://researcher.branch.zeropath.com/blog/cve-2026-42809-apache-polaris-credential-vending-bypass)). Unity Catalog OSS had a critical JWT issuer bypass allowing full user impersonation ([GitHub advisory](https://github.com/unitycatalog/unitycatalog/security/advisories/GHSA-qqcj-rghw-829x)). Nessie had a high-severity S3 remote-signing bypass in November 2026 ([Nessie advisories](https://github.com/projectnessie/nessie/security/advisories)). Lakekeeper shows only dependency (RustSec) bumps, but its release cadence is fast. So the rules are: pin the latest patch, bind the catalog to `graphguard-net` or 127.0.0.1 only, never put it behind nginx, and treat credential vending as the piece most likely to have the next bug.

## Real S3 beats self-hosted storage, and MinIO is off the table

**Upstream MinIO community edition is dead.** The `minio/minio` repo is archived. Its last release is `RELEASE.2025-10-15T17-29-55Z` ([GitHub API](https://api.github.com/repos/minio/minio/releases)). Binary and Docker distribution stopped in October 2025, and TuxCare lists 2026 CVEs affecting that last release with no community fixes ([TuxCare](https://tuxcare.com/blog/minio-els/)). Sources disagree on the archive date (February 12/13 vs April 2026). The GitHub push date of 2026-04-24 suggests the repo was archived twice. The only maintained fork is `pgsty/silo`, a one-vendor AGPL fork that has dropped the MinIO name ([GitHub API pgsty/silo](https://api.github.com/repos/pgsty/minio/releases)). Most reference builds still use MinIO. A reviewer who sees `minio/minio` in a late-2026 repo will read it as unpatched software.

**AWS S3 in us-east-1 is the most "Databricks-like" choice and costs zero RAM on the box.** It has real IAM JSON policies, conditional writes since August 2024 ([AWS](https://aws.amazon.com/about-aws/whats-new/2024/08/amazon-s3-conditional-writes)), and the first 100GB/month of egress free ([AWS S3 pricing](https://aws.amazon.com/s3/pricing/)). Storage at 50GB comes to about **$1.15/month** (estimate, from the standard ~$0.023/GB rate). The project already plans its own bucket and scoped IAM user, so this adds no new vendor. The data also leaves the 25GB local disk. Cheaper options exist: Cloudflare R2 has 10GB free and zero egress ([R2 pricing](https://developers.cloudflare.com/r2/pricing/)), and Backblaze B2 costs ~$0.007/GB ([B2 pricing](https://www.backblaze.com/cloud-storage/pricing)). But they are less "real". B2 also holds the restic backups, so mixing in lakehouse data widens the blast radius. Hetzner Ashburn and us-east-1 are both in Northern Virginia, so latency should be a few ms. That is inference. Measure it with `curl -w` from the box.

**If self-hosting is a goal in itself, use Garage and know its gaps.** Garage v2.5 has a one-flag `--single-node` mode ([Garage v2.3.0 notes](https://git.deuxfleurs.fr/Deuxfleurs/garage/releases/tag/v2.3.0)), and third parties report under 20MB idle and under 200MB under stress ([VSHN ADR](https://kb.vshn.ch/app-catalog/adr/0050-alternatives-to-minio-for-s3-compatible-object-storage.html)). Those are published, not measured here. But it has **no bucket policies, no versioning, no object lock** ([Garage S3 compat](https://garagehq.deuxfleurs.fr/documentation/reference-manual/s3-compatibility/)). It also **silently overwrites** on `If-None-Match: *` instead of refusing ([Garage #1326](https://git.deuxfleurs.fr/Deuxfleurs/garage/issues/1326)). That does not break Iceberg with a SQL or REST catalog, because the catalog does the commit. It does break catalog-less "pointer file" designs and multi-writer Delta. SeaweedFS (Apache-2.0, ~256MB published) and RustFS (Apache-2.0, 1.0 GA only in September 2026) cover more of the S3 API. Ceph is far too heavy. Garage fits best as a CI or local test target, which shows that storage is an abstraction.

One local caveat: **DuckDB's REST write path supports only S3, S3 Tables and GCS** ([DuckDB docs](https://duckdb.org/docs/current/core_extensions/iceberg/writing)). A `file://` warehouse works for Polars and PyIceberg but not for DuckDB writes. That fixes the build order: local disk first, then S3, then the REST catalog.

## Three in-process engines cover today, and Spark becomes a job

**Polars stays the feature engine.** `scan_iceberg` reads natively, and `write_iceberg`/`sink_iceberg` append or overwrite through PyIceberg. Both writers are marked **unstable**, and neither does merge or upsert ([Polars docs](https://docs.pola.rs/api/python/dev/reference/api/polars.DataFrame.write_iceberg.html)). **DuckDB 2.0** is the only non-JVM engine with Iceberg INSERT, UPDATE, DELETE and **MERGE INTO** on partitioned tables. It needs a REST catalog, and it writes merge-on-read delete files only ([DuckDB 2.0 docs](https://duckdb.org/docs/2.0/core_extensions/iceberg/writing_to_iceberg.html)). It also has `ASOF JOIN` for point-in-time checks, a localhost-only server mode, and a built-in SQL notebook UI ([DuckDB 2.0.0](https://duckdb.org/2026/10/21/announcing-duckdb-200); [DuckDB UI](https://duckdb.org/docs/current/core_extensions/ui)). **PyIceberg 0.12** is the admin library: it creates tables, upserts and expires snapshots ([releases](https://github.com/apache/iceberg-python/releases)). Its upsert is dangerous at scale: one user reports **~80GB RAM for a 34M-row upsert** ([discussion #3118](https://github.com/apache/iceberg-python/discussions/3118)). So design tables to be **append-only**, and use DuckDB MERGE for the one table that needs updates (labels that become known later).

**The real gap without a JVM is maintenance.** DuckDB has no compaction or expiry call. PyIceberg can expire snapshots but cannot compact or remove orphan files, and one tester found expired data files still on disk ([Hikmah Technologies](https://hikmahtechnologies.com/blog/iceberg-table-maintenance/); [issue #1092](https://github.com/apache/iceberg-python/issues/1092)). Only Trino (`optimize`, `remove_orphan_files`, [Trino 480](https://trino.io/docs/current/release/release-480)) and Spark do full maintenance. At 5M rows, "compact by rewriting the table" is cheap. At 180M rows it is not, and that is where Spark earns its place.

**Spark and Trino do not fit as resident services.** Spark's driver default is 1g, and my estimate for local mode with Python workers is ~1.5–2GB RSS. Trino production guides use 64GB nodes ([Cloudera](https://docs.cloudera.com/cdw-runtime/1.5.5/trino-performance-tuning/trino-performance-tuning.pdf)), and a 2GB heap is my estimated floor for anything more than toy queries. Either one alone exceeds the ~1GB spare. So Spark comes in for the 180M-row phase as a capped container that starts, runs, and stops, against the same REST catalog. Use Spark 4.1 with `iceberg-spark-runtime-4.1_2.13` at Iceberg 1.11 or later. Mixing runtimes gives `AbstractMethodError` ([Acceldata](https://docs.acceldata.io/odp/documentation/apache-spark-4-1-1)). Databricks Free Edition is fine for a learning demo, but it is capped at a 2X-Small warehouse and forbids commercial use ([Databricks](https://docs.databricks.com/aws/en/getting-started/free-edition-limitations)).

**The leakage contract needs one explicit test.** Polars `join_asof(allow_exact_matches=False)` and DuckDB's strict `>` both give "strictly before" semantics. Neither Databricks' nor Feast's point-in-time docs settle what happens with same-timestamp ties ([Databricks](https://docs.databricks.com/aws/machine-learning/feature-store/time-series)). Write a unit test where a transaction shares a timestamp with an earlier one, and assert that it cannot see itself.

## Most of Databricks maps to things that cost zero RAM

The heavy ones do not fit: OpenMetadata needs **16GiB** ([docs](https://docs.open-metadata.org/latest/deployment/minimum-requirements)), DataHub **8GB** ([quickstart](https://datahubproject.io/docs/quickstart)), Superset **8GB** for a single-host eval ([Canonical](https://canonical-data-mesh-documentation.readthedocs-hosted.com/en/latest/reference/superset/system-requirements/)), and Airflow 3 recommends **at least 4GB** ([Airflow](https://airflow.apache.org/docs/apache-airflow/3.1.0/installation/prerequisites.html)), which is the whole project budget. Everything else can be a library, a CLI run, or a UI started over an SSH tunnel.

Two items here give the most value per MB, and both tie straight into the leakage contract. The first is **training-set versioning**: every run logs (silver snapshot id, gold snapshot id, `frozen_split.json` sha256, git sha), and a test re-reads the old snapshot by time travel and gets identical rows. Dremio and Cloudera both describe this snapshot-id-as-param pattern ([Dremio](https://www.dremio.com/blog/apache-iceberg-machine-learning-solving-data-versioning-for-ai/); [Cloudera](https://community.cloudera.com/t5/Community-Articles/Logging-Iceberg-Metrics-with-MLFlow-Tracking-in-CML/ta-p/385657)). The second is my own inference, not something a source describes: **use catalog grants to seal the test set.** Put the test window in its own namespace and give the training principal no read grant on it. Contract rule 4 then becomes a permission denial with a negative test, in addition to the `test_set_touch_check` lint. Few portfolio lakehouses can show governance doing real work like that.

On orchestration, Dagster's software-defined assets fit a lakehouse best: each Iceberg table is an asset with lineage and checks. Prefect announced in July 2026 that it is acquiring Dagster Labs, and Dagster keeps its name and open-source licence ([Dagster blog](https://dagster.io/blog/prefect-is-acquiring-dagster)). The closing date is unverified. My estimate for a resident Dagster webserver plus daemon is ~0.5–1GB. That does not fit beside Ray at peak, so run `dagster asset materialize` from a systemd timer and start the UI only for demos. The tension is real, though: **Airflow appears in 51 of 139 postings and Dagster in 4.** If Phase 8 picks on hiring value, a minimal LocalExecutor Airflow must be measured, and its 4GB official recommendation suggests it will not fit.

## Iceberg is a niche keyword; the capabilities around it are what get hired

The November 2026 sample of 139 postings (103 fintech/payments/AML, 36 tech) shows the everyday stack employers ask for: **Spark 39%, Airflow 37%, Kafka 25%, Snowflake 24%, data quality 22%, dbt 20%, Databricks 15%**. Iceberg shows up in 7% (10 postings), "lakehouse" in 6%, and Polaris, Hudi, SQLMesh, DuckDB and "medallion" in none. All 10 Iceberg postings are data-platform roles, mostly senior or staff. Examples: Stripe Risk Data Engineering lists "Iceberg, Kafka, Change Data Capture, Flink, Spark, Airflow, Hive Metastore, Pinot, Trino" ([Stripe](https://stripe.com/jobs/search?gh_jid=8112043)), and TRM Labs, an AML firm, asks for "Iceberg, Trino, BigQuery, and StarRocks" ([TRM Labs](https://jobs.ashbyhq.com/trm-labs/990a102e-3596-49ac-b527-9addc25771c4)). **None of the 79 ML-engineer or ML-platform postings mention Iceberg or lakehouse.** Surveys agree: dbt Labs' 2026 survey (n=363) finds 9% using Iceberg in production and 68% with no plans ([dbt Labs](https://www.getdbt.com/resources/state-of-analytics-engineering-2026)). The same survey names "knowledge gaps" as the top barrier (27%). So someone who has actually run catalogs and maintenance has a rare skill, even if few job ads name it.

What carries weight is the **capability language** in senior postings. SoFi wants "data contracts, metadata and catalog modernization, lineage, data quality, privacy, and access controls" ([SoFi](https://sofi.com/careers/job/8037984003?gh_jid=8037984003)). Coinbase wants "reconciliation frameworks (tests, monitoring, alerting, SLAs)" ([Coinbase](https://www.coinbase.com/careers/positions/8047150?gh_jid=8047150)). Toast's staff data-platform role pairs a "cloud-native data lakehouse" with "feature serving for ML-driven product experiences" ([Toast](https://careers.toasttab.com/jobs?gh_jid=8068781)). For an ML candidate, the right framing is **"the lakehouse is the reproducibility and point-in-time layer under my model."** "I used Iceberg" is the weak version. The lakehouse also gives Spark (the most-requested tool) a natural home later.

The reference builds show what to avoid. The most instructive one, technobasant/lakehouse-lab (Polaris, MinIO STS, Trino, StarRocks, dbt, Airflow), needs **about 8 CPUs and 12GB** ([GitHub](https://github.com/technobasant/lakehouse-lab)). Its strengths are measured results: compaction from 20 files to 1, a rollback that recovered 909,968 rows in 589 ms, and a test proving that vended credentials are denied on a sibling table. It also needed three MinIO-vs-S3 workarounds and hit a Polaris bug where the server reported healthy on an empty database. The canonical Spark + Iceberg REST quickstart is databricks/docker-spark-iceberg ([GitHub](https://github.com/databricks/docker-spark-iceberg)). **None of these repos reports per-service RAM.** A trimmed build with a measured RAM table, real S3, and the lakehouse tied to a working model would stand out from every one of them.

## Recommended architecture for this box

**The build.** Use Iceberg v2 tables in bronze/silver/gold namespaces. Files live in a dedicated lakehouse prefix or bucket inside GraphGuard's own AWS account, with its own scoped IAM user, and nothing belonging to `aws-job-streamer` is touched. Lakekeeper is the REST catalog: a Docker Compose service on `graphguard-net`, never exposed, with its database inside the existing MLflow Postgres. Polars, DuckDB and PyIceberg run as capped jobs. Redis is rebuilt *from* `gold.account_features_asof`, so it stops being the only copy. Every MLflow run logs its snapshot ids. Spark arrives later as a batch job against the same catalog.

**RAM budget** (M = measured on the box, P = published by a third party, E = my estimate):

| Component | Resident | Peak / job-time | Label |
|---|---|---|---|
| Existing: k3s 792, Ray Serve 1,965 (peak), MLflow 96 idle, Postgres 22, Redis 32, runner 21 | ~2.93GB | MLflow up to ~700MB busy (+~600MB) | M |
| Lakekeeper (cap 256M to start) | ~30–100MB | small: it serves only metadata | E (no published figure) |
| Catalog database in the existing Postgres | +10–30MB | — | E |
| AWS S3 | 0 | 0 | — |
| DuckDB (`SET memory_limit='512MB'`, spill dir) | 0 | ≤512MB | E (enforced by the cap) |
| Polars write + Redis rebuild | 0 | measure with `/usr/bin/time -v` | to measure |
| Feast, Pandera, OpenLineage, marimo, DuckDB UI | 0 | small, on demand | E |
| OpenFGA (optional, for RBAC) | ~50–150MB | — | E (not researched) |
| Dagster (UI on demand only) | 0 | ~0.5–1GB while the UI runs | E |
| Garage (optional, CI only) | <20MB idle | <200MB stress | P |
| Spark local (Phase 10) | 0 | ~1.5–2GB | E |

New resident cost is about **0.05–0.3GB**. That fits the ~1GB spare. The real risk is overlap at peak: Ray at peak + MLflow busy + a 512MB DuckDB job comes to about 4.0GB, right at the budget. So **lakehouse jobs must not run during MLflow-heavy training**, and Spark cannot run while Ray sits at peak. Run Spark with Ray scaled down, or on a rented box.

**Build order.** Every step ends with a measurement gate: `docker stats --no-stream` idle, then under a 5M-row write, written into the repo the way the Ray decision was. A step stays only if it fits.

| Step | What | New resident RAM | Gate |
|---|---|---|---|
| L0 | Baseline: `free -h`, `docker stats`, peak RSS of today's Polars→Redis job | 0 | Numbers recorded |
| L1 (S5.6) | Iceberg v2 tables on local disk. PyIceberg SQL catalog in a new database on the existing Postgres (SQLite or in-memory only in CI). Polars writes; Redis rebuilt from gold; snapshot ids in MLflow; time-travel test; one Pandera schema per layer; `expire_snapshots` | 0 | Parity, leakage and determinism tests pass. Disk measured |
| L2 | Move the warehouse to S3 (own prefix/bucket and IAM user, after Lubo's sign-off). Add DuckDB 2.0: reads, ASOF parity check against Polars. Measure RTT | 0 | Same results from S3 as from local disk |

| L4 | Governance: OpenFGA grants, STS-vended credentials, test-namespace denial with a negative test | E 50–150MB | Measured. Optional if RAM is short |
| L5 | Feast (library) DuckDB-offline over Iceberg → Redis, asserted equal to Polars output. OpenLineage audit table. marimo worksheets | 0 | Parity test passes |
| L6 (Phase 8) | Dagster assets on a timer (or minimal Airflow if measured to fit). Maintenance job: expire, orphan sweep, compaction by rewrite | 0 resident | Scheduled runs green |

Starting any container needs Lubo's approval under the box rules. Never use MinIO (or its Silo fork), Unity Catalog OSS (2.76GB image), OpenMetadata, DataHub or Superset here.

## Conclusion

The surprise is how little of a "real" lakehouse needs to run all the time. The catalog is the only true server. Everything Databricks sells as a platform layer (medallion, expectations, lineage, notebooks, the feature store link) reduces here to conventions, libraries and jobs, as long as the files sit in real S3 and the catalog speaks Iceberg REST. That changes the question from "can a 4GB box host a lakehouse?" to "can every job stay inside its cap and avoid the Ray and MLflow peaks?" The measured RAM table answers that, and it is also the piece no public reference build has.

The hiring data gives the owner permission to build this for the joy of it, not as a keyword play. Iceberg will not get an ML resume past a filter. A lakehouse that seals the test set with a permission denial, rebuilds Redis from a versioned snapshot, and lets any model be traced back to its exact training rows shows senior judgement in any interview. And Spark, the most-requested skill in the sample, will arrive in Phase 10 with a home already waiting for it.
