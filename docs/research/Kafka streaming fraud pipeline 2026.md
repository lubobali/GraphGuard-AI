# Build the stream small, exact and provable

GraphGuard-AI should build Phase 6 as **one Apache Kafka 4.4.0 broker** (official JVM image, KRaft combined mode, heap cut to about 256-384 MB under a 768 MB cap, SCRAM logins and deny-by-default ACLs), fed by a **paced replayer** that sends only the validation window in `(timestamp, source_row)` order, and read by a **plain Python consumer** (confluent-kafka 2.16.x) that updates exact features in Redis with one atomic Redis Function per transaction, scores XGBoost in process, and writes each decision to Postgres in the same database transaction as its Kafka position. Kafka's own "exactly-once" does not reach Redis or Postgres, so "effectively-once" comes from at-least-once delivery plus sinks that ignore repeats: a primary key on the event id in Postgres and a per-account watermark in Redis. Flink, RisingWave and similar engines do not fit: Flink's shipped defaults alone ask for about 3.3 GB, close to the whole project budget. The realism a senior reviewer looks for is not more tools. It is the hard parts that demo projects skip: deterministic replay that gives the same decisions at any speed, seeded faults that change nothing, labels that arrive late, a rules baseline, shadow scoring, and a row-by-row proof that the stream computes the same features as training. That proof currently fails in two known places in the code (money totals seeded with `sum()` instead of `cum_sum()`, and an inclusive 24-hour boundary where training is exclusive), so fixing them comes right after the scorer-down alert. The new stream parts should add roughly **1.3-1.6 GB at their caps**, all of it to be measured before it is committed. The data stays synthetic (IBM AMLworld, about 50 hours of validation replay), and every write-up should say so first.

A few words used throughout. A **topic** is a named log in Kafka. A **partition** is one ordered slice of a topic; Kafka keeps order only inside a partition. An **offset** is a record's position in a partition. A **consumer group** is a set of readers that share a topic and remember how far they have read. **Idempotent** means doing something twice has the same effect as doing it once.

## Kafka 4.4.0 on one node fits, if the heap is cut and every replica count is 1

**Pick Kafka 4.4.0, released 22 October 2026.** The Apache downloads page lists only 4.4.0, 4.3.2 and 4.2.2 as supported; everything else is archived ([Kafka downloads](https://kafka.apache.org/community/downloads/)). The version floor matters because 2026 brought many broker CVEs, mostly crashes or out-of-memory from crafted requests (for example CVE-2026-114349 and CVE-2026-111108), and nearly all of them are fixed only in 4.2.2, 4.3.2 and 4.4.0. One, CVE-2026-112375, lets an unauthorized principal read broker files and environment variables through IncrementalAlterConfigs. Another, CVE-2026-41115, makes group-describe check the wrong permission and has **no fixed release** on the list, so the advice is to review group ACLs ([Kafka CVE list](https://kafka.apache.org/community/cve-list/)). Both are reasons to give each client its own login with the smallest set of rights. Kafka 4.0 was the first release with no ZooKeeper at all. Its built-in metadata system is called **KRaft**. It also made the new consumer rebalance protocol (KIP-848) generally available, but clients must opt in with `group.protocol=consumer` ([4.0 announcement](https://kafka.apache.org/blog/2025/03/18/apache-kafka-4.0.0-release-announcement/)). One 4.4 change is a trap for scripts: a broker must now be the same version as, or newer than, the `kafka-storage` tool that formatted its data directory ([4.4.0 announcement](https://kafka.apache.org/blog/2026/10/22/apache-kafka-4.4.0-release-announcement/)). Format and run with the same pinned image.

**Use the JVM image `apache/kafka`, not `apache/kafka-native`.** Apache calls the native GraalVM image "experimental and intended for local development and testing purposes only" ([Kafka 4.4 Docker docs](https://kafka.apache.org/44/getting-started/docker/)). It is much lighter, about 230-250 MB in its 2023 benchmark against about 1 GB for the JVM broker ([KIP-974](https://cwiki.apache.org/confluence/display/KAFKA/KIP-974:+Docker+Image+for+GraalVM+based+Native+Kafka+Broker)). But a project whose bar is "a reviewer cannot find the shortcut" should not run a dev-only image as its production broker. Native can still appear as a measured footnote, or as the CI test broker. The JVM image bundles its own Java runtime (Temurin 25 on Alpine in the current Dockerfile) and runs as a non-root `appuser` with no fixed numeric ID ([JVM Dockerfile](https://raw.githubusercontent.com/apache/kafka/trunk/docker/jvm/Dockerfile)). So pin the image by digest, pin `user:` to the numeric ID found in that digest, and check `java -version` against the JDK flaw disclosed on 17 November 2026 (CVE-2026-114938, "Java4Shell", in the HotSpot Base64 decoder; severity is disputed between 8.1 and 9.2) ([Strobes](https://strobes.co/blog/java4shell-cve-2026-114938-openjdk-base64-rce/)). If the published digest predates the JDK fix, wait for a rebuild or build on a patched runtime.

**Memory is the real constraint, not throughput.** The start script sets a 1 GB heap (the JVM's main memory pool) when nothing else is given ([kafka-server-start.sh](https://raw.githubusercontent.com/apache/kafka/trunk/bin/kafka-server-start.sh)). The most recent measurement found, on `apache/kafka:4.3.1` in October 2026, shows a single KRaft broker at **402 MiB** with that default heap, and brokers that idle at about 300 MiB but grow to **1.1 GiB** under a benchmark as the heap fills ([ComputingForGeeks](https://computingforgeeks.com/deploy-kafka-docker-compose/)). No source measured a 4.x broker with a small heap under load. So the starting point, `-Xms256m -Xmx384m` plus limits on direct memory and metaspace inside a 768 MB container cap, is an extrapolation and must be measured with `docker stats` and the cgroup's peak memory during a fast replay. Kafka leans on the operating system's page cache (file data kept in RAM), which counts toward the container's memory but can be reclaimed, so a tight cap mostly shrinks the cache. Heap, metaspace, direct buffers and thread stacks are the hard floor. The load is tiny for Kafka: validation holds 1,015,300 transactions over about 50.6 hours (`data/splits/frozen_split.json`), and the busiest minute is 187 tx/s, so even a 100x replay is about 19,000 events per second.

**Single-node KRaft needs every internal replica count set to 1.** Run combined mode (`process.roles=broker,controller`). Apache says combined mode "is not recommended in critical deployment environments" ([KRaft operations](https://kafka.apache.org/44/operations/kraft/)), and the write-up should say that plainly: it is a one-node limit, not a hidden one. Bootstrap the current documented way, with `kafka-storage.sh format --standalone` and `controller.quorum.bootstrap.servers`, not the static `controller.quorum.voters` most blog posts still show ([KRaft operations](https://kafka.apache.org/44/operations/kraft/)). Set the offsets topic, the transaction state log and the share-coordinator state topic to replication factor 1 and minimum in-sync replicas 1; the defaults ask for three replicas, "which one broker can't provide" ([ComputingForGeeks](https://computingforgeeks.com/deploy-kafka-docker-compose/)). Add `auto.create.topics.enable=false` so only the admin job creates topics, small segments (64-128 MB) so retention can actually delete, and size-based retention. One caution that comes from Kafka's behaviour rather than from the notes: time-based retention judges a segment by the newest record timestamp in it, and AMLworld's event times are from 2022. If the record timestamp is set to the 2022 event time, a normal `retention.ms` would treat the data as years old and delete it. Either keep the record timestamp as the wall-clock send time and carry event time in the payload and a header, or turn time retention off for the replay topics and rely on size. The first is simpler and keeps "when Kafka saw it" honest.

**Security on one box: SCRAM logins, deny by default, one principal per job.** SCRAM is Kafka's username-and-password login that never sends the password itself. Apache says SCRAM and PLAIN "should be used only with TLS" ([SASL docs](https://kafka.apache.org/44/security/authentication-using-sasl/)). The listeners here are reachable only from the host and from the k3s pod network, never from the internet, so SASL/SCRAM-SHA-512 without TLS still gives real per-client identities and ACLs (access control lists: which login may do what), and the remaining risk is local sniffing by someone who already has root. That trade-off should be written in an ADR; adding TLS with a private CA is the textbook answer and costs little CPU at this load. Use the StandardAuthorizer with `allow.everyone.if.no.acl.found=false`, and create separate principals for the replayer (write to `transactions`), the consumer (read `transactions` and its group, write `decisions`, `alerts` and the dead-letter topic), an admin used only by setup, and a describe-only monitor. SCRAM credentials can be added at format time with `--add-scram` ([SASL docs](https://kafka.apache.org/44/security/authentication-using-sasl/)), and they belong in the existing secrets registry, with the pod's credential as a Kubernetes Secret, the same pattern as Redis. The classic networking bug is `advertised.listeners`: a client connects, then is told to reach an address it cannot reach. The official image even derives a listener that binds every interface when listeners are unset ([configure script](https://raw.githubusercontent.com/apache/kafka/trunk/docker/resources/common-scripts/configure)), so set them explicitly: one listener per network, each advertising the address its own clients see, and the controller listener never published. Kafka 4.4 helps debug this by detecting misrouted connections (KIP-1242) ([4.4.0 announcement](https://kafka.apache.org/blog/2026/10/22/apache-kafka-4.4.0-release-announcement/)). The pod-side NetworkPolicy will hit the same post-DNAT address trap the Redis policy already solved (`k8s/networkpolicy.yaml`).

**The alternatives do not beat it.** Redpanda 26.3.1 (20 November 2026) ended source availability; its free Community Edition is now a binary limited to 50 cores per organization ([Redpanda](https://www.redpanda.com/blog/r2-the-engine-of-engines)), which confirms the earlier R-2 decision to swap it for Kafka (`docs/research/AML portfolio plan research 2026.md`). Bufstream recommends three replicas of 8 GiB each ([Bufstream](https://buf.build/docs/bufstream/deployment/cluster-recommendations)), and object-storage designs like WarpStream and AutoMQ are built for multi-zone clusters. Tansu, a Rust broker that can write Iceberg tables, is interesting but a single-maintainer 0.x project with an inconsistent licence ([tansu-io/tansu](https://github.com/tansu-io/tansu)). For monitoring, consumer-group lag does not come from the broker's JMX metrics; a small exporter such as `kafka_exporter` reads it through the Admin API, while the JMX agent runs inside the broker's JVM and eats its memory budget ([OneUptime](https://oneuptime.com/blog/post/2026-01-21-kafka-monitoring-prometheus-grafana/view)). Skip the JMX agent until a specific broker metric is needed.

## Effectively-once comes from idempotent sinks, not Kafka transactions

**Use confluent-kafka-python 2.16.x.** It wraps the C library librdkafka and, in November 2026, is the only Python client with generally available KIP-848 support (since 2.12.0), transactions, non-experimental asyncio classes, and wheels up to Python 3.15 ([CHANGELOG](https://github.com/confluentinc/confluent-kafka-python/blob/master/CHANGELOG.md)). aiokafka and kafka-python are pure Python and active, but neither supports KIP-848, and kafka-python supports the Kafka 4.0 transaction protocol only partly ([kafka-python KIPs](https://kafka-python.readthedocs.io/en/master/kips.html)). Synchronous `Producer` and `Consumer` are enough: scoring is CPU-bound at about 0.6 ms per event, so asyncio buys nothing. Pin it under the project's 14-day rule.

**On the producer side, turn on idempotence.** With `enable.idempotence=true`, librdkafka forces `acks=all`, at most 5 requests in flight, unlimited retries and FIFO queueing, which removes duplicates and reordering caused by retries ([librdkafka CONFIGURATION.md](https://github.com/confluentinc/librdkafka/blob/master/CONFIGURATION.md)). On one broker `acks=all` means the same as `acks=1`, but it keeps the code shaped for production. Idempotence only works inside one producer session. If the replayer is killed and restarted, it must resume from a durable checkpoint (the last `source_row` whose delivery was confirmed), and every message carries `event_id = source_row` so the consumer can drop any re-send.

**Kafka's exactly-once stops at Kafka.** Kafka transactions make a read-process-write loop exactly-once only when both input and output are Kafka topics ([Confluent](https://www.confluent.io/pt-br/blog/exactly-once-semantics-are-possible-heres-how-apache-kafka-does-it/)). Redis and Postgres sit outside that transaction. The standard pattern for an external database is to store the consumed offset in the same database transaction as the results, and to seek to that stored offset on start ([Kafka users list](https://go.mail-archive.com/users@kafka.apache.org/msg30622.html)). So the design is: per micro-batch, one Postgres transaction does `INSERT ... ON CONFLICT (event_id) DO NOTHING` into `decisions` and upserts `consumer_offsets(topic, partition, next_offset)`. On assignment the consumer reads that table and seeks there. Committing offsets to Kafka afterwards is only for lag monitoring. A crash between the Postgres commit and the Kafka commit then cannot count anything twice. `DO NOTHING` is right, not `DO UPDATE`: the first decision is the audit record and a replay must never overwrite it. A statement may not touch the same row twice, so de-duplicate inside each batch first ([PostgreSQL INSERT](https://www.postgresql.org/docs/current/sql-insert.html)).

**Redis needs its own idempotency, because it cannot join the Postgres transaction.** A Redis script runs atomically and blocks the server while it runs, and it can make conditional updates across several keys ([Redis scripting](https://redis.io/docs/latest/develop/programmability/eval-intro/)). Each account hash keeps a **watermark**, the `(timestamp, source_row)` of the last event applied to it. The script applies an update only if the incoming pair is strictly larger, so a re-delivered event becomes a no-op. This works exactly because the order is total. One crash window remains: if the consumer dies after the Redis update but before Postgres commits, the replayed event looks like a duplicate and its "before" features are gone. The fix is for the same script to write `pending:{source_row}` holding the before-state, and for the consumer to delete it after the Postgres commit. On a replay it scores from `pending:*`, or skips if the decision row already exists. Every step is then idempotent: Redis Function, score, Postgres commit, delete pending, commit Kafka offset. A crash anywhere is safe.

**Bound memory, split failures into two kinds, and shut down cleanly.** librdkafka's defaults are generous for a small box: the consumer may prefetch 64 MB and the producer may queue up to 1 GB ([CONFIGURATION.md](https://github.com/confluentinc/librdkafka/blob/master/CONFIGURATION.md)). Cap them (around 8-16 MB of prefetch and a 32 MB producer queue, then measure) and treat a full producer queue as backpressure. Failures come in two kinds. A **poison** record (bad schema, impossible values) can never succeed, so it goes to a **dead-letter queue** (DLQ, a side topic for records that could not be processed) with the error and its source offset, is counted in the same batch, and the stream moves on. A **transient** failure (Redis or Postgres down) must never go to the DLQ: the consumer calls `pause()`, keeps polling so it is not thrown out of its group, and retries the whole batch. That maps onto the scorer's existing 503 rule: no store marker, no scoring. A schema registry is not worth its memory here; vendor estimates put the lightest open ones at 200-300 MB ([AxonOps](https://axonops.com/blog/comparing-kafka-schema-registries/), a competing vendor). Versioned JSON with a `schema_version` field and a Pydantic model per version, tested as a contract, does the same job for one producer and one consumer. On SIGTERM: finish the batch, commit to Postgres, flush the producer, close the consumer.

## Replay is only realistic if the decisions do not depend on how it is replayed

**Keep two clocks and let correctness depend on only one.** Event time is when a transaction happened; processing time is when the system saw it. Correct results come from analysis by event time ([Streaming 102](https://oreilly.com/ideas/the-world-beyond-batch-streaming-102)), and event time can move faster than the wall clock, which is what makes accelerated replay possible ([Flink docs](https://ci.apache.org/projects/flink/flink-docs-master/docs/concepts/time/)). The replayer should offer three pacing modes as one setting: true time (50 hours for validation), accelerated by a factor (x60 replays validation in about 51 minutes), and as fast as possible (for backtests and load tests). All three must give **byte-identical decisions**, and a CI test should prove it on a slice. Nothing in a feature may read `datetime.now()`.

**Ties need one fixed order, and that order needs one partition.** 9.4% of transactions share a minute with another (FINDING-010), so the total order is `(timestamp, source_row)`, written into each message as an explicit `seq`. Kafka orders records only within a partition. If the topic were keyed by sender, a receiver's updates would arrive from many partitions with no relative order, and same-minute ties could be applied differently from training. **One partition is the honest choice** for about a million events, and the ADR should name it as the scaling limit; the scale-out answer is a second stage re-keyed by receiver. When pacing, the replayer can spread a minute's events evenly across that minute of wall-clock time, but it must not invent sub-minute event times.

**The replay sends only the validation window.** The source is `silver.transactions` filtered to `train_end <= timestamp < val_end` (2022-09-06 13:34 to 2022-09-08 16:09). The test window lives only in `sealed.transactions`, which the reader identity cannot see at all, so the guard is a permission and not a list. The replayer should still assert that its largest timestamp is below `val_end`, and `test_set_touch_check` should keep counting call sites. This makes the whole stream a **backtest on validation**: allowed for tuning, never a claim about test performance.

**Inject imperfections at the transport layer, never in the event fields.** Every fault should be seeded and written to a fault log. The useful ones are: duplicates (re-send a seeded fraction with the same id, or kill the consumer between its write and its commit); late arrival (hold back 1-2% and send it later in wall-clock time, with event time unchanged); malformed records (missing field, negative amount, unknown currency) that must land in the DLQ; bursts from the pacing multiplier to test lag and backpressure; broker restarts; and consumer `kill -9` at seeded points. Tools exist for parts of this: Toxiproxy adds latency and cuts connections but does not duplicate or reorder ([Conduktor glossary](https://conduktor.io/glossary/chaos-engineering-for-kafka)), and Conduktor Gateway has a duplicate-message interceptor ([Conduktor docs](https://docs.conduktor.io/guide/use-cases/chaos-testing)). For this project the replayer itself can do it, which keeps the faults seeded and logged. The strongest single piece of evidence for a reviewer is **"decision parity under chaos"**: a replay with faults gives exactly the same decisions as a clean replay, except for the rows the fault log says should differ (the DLQ). Late events are a special case for cumulative features: inserting one "in the past" would change values already served, so exact parity with batch is impossible for them. In the ordered replay the late count should be zero by construction; assert it as a counter, and when lateness is injected on purpose, apply the event, flag the decision `late`, and exclude those rows from the parity check by an explicit rule.

**Labels must arrive late, mostly for alerted cases.** Dal Pozzolo and colleagues showed that most fraud papers "ignore the verification latency" and modelled two label streams: quick investigator feedback on the top-k alerts each day, and delayed labels for everything else after δ days (δ = 7 in their experiments). Feedback labels carry selection bias because the model chose them ([Dal Pozzolo et al., TNNLS](https://boracchi.faculty.polimi.it/docs/2017_FraudsTNNLS.pdf)). AML is slower than card fraud: a US SAR is due 30 days after *detection*, at most 60 ([31 CFR 1020.320](https://www.ecfr.gov/current/title-31/subtitle-B/chapter-X/part-1020/subpart-C/section-1020.320)), and undetected laundering may never be labelled. AMLworld's "perfect tagging" is itself unrealistic ([Altman et al.](https://arxiv.org/abs/2306.16424v3)). So labels go on a separate `labels` topic with `{event_id, label, label_source, label_known_at}`: investigator verdicts at alert time plus a seeded review delay, limited by a daily capacity k, and "delayed truth" for unalerted laundering at event time plus 30-120 days, with some never arriving. The validation window is only about 50 hours long, so at any realistic delay almost no delayed labels arrive inside it. That is a finding to state plainly; a compressed δ can be offered as a clearly labelled what-if. Evaluation should report precision@k with eventual labels and the metric as it was visible at each moment, following continuous re-evaluation under delayed labels ([Grzenda et al.](https://link.springer.com/article/10.1007/s10618-019-00654-y)). The existing `gold.labels.label_known_at` column is where the leakage contract extends to labels.

## Exact streaming features need integers, one atomic script, and a row-by-row test

**Two obvious Redis tools break exactness.** `HINCRBYFLOAT` keeps a 17-decimal string from its own computation, not the float64 Polars produces ([Redis INCRBYFLOAT](https://redis.io/docs/latest/commands/incrbyfloat/)). HyperLogLog counts distinct items with about 0.81% error ([Redis HyperLogLog](https://redis.io/docs/latest/develop/data-types/probabilistic/hyperloglogs/)). Both are out.

**The first parity gap: money totals.** A measurement on this box over train and validation (the test window was not read) found that Polars `cum_sum()` on float64 is bit-identical to a plain sequential sum, but Polars `sum()` is not: it uses a compensated method, and over all amounts the two differ by about 3.9 units in 22.9 trillion. Training builds `amount_sent_before` with `cum_sum().over(account) - amount` (`src/graphguard/features/graph.py`), while the snapshot that seeds the online store uses `sum()` (`account_states_frame` in `src/graphguard/serving/online_features.py`). So the stream starts from slightly different numbers than training saw. The clean fix is **integer micro-units** everywhere: parse the amount string straight to an integer of millionths (never `float * 1e6`, since amounts up to 1e12 with 6 decimals need about 19 digits and float64 holds about 16), sum with `HINCRBY` online and integer `cum_sum` in batch, and convert to float only when building the model row. Integer sums are exact and do not depend on order. The largest per-account total is about 1.5e18 micro-units, inside int64 with about 6x headroom; Phase 10 must re-check that. This changes the training features in their last bits, so it needs a rebuild of features and a retrain through `just build-artifacts`, scored on validation only. If keeping the current model bit-for-bit matters more, the fallback is to seed with the sequential `cum_sum` value per account and repeat float64 addition in Python, computing "before" as `(old + a) - a` exactly as batch does.

**The second parity gap: the 24-hour boundary.** Training computes `sent_last_24h` with a backward as-of join, so a send exactly 24 hours earlier is **excluded** and same-minute sends with a smaller `source_row` are included. The snapshot code uses `timestamp >= window_start`, which **includes** it (`features/graph.py`, `serving/online_features.py`). Training defines what the model learned, so the snapshot must change to match it. A seeded count also cannot roll forward, so the snapshot must carry the actual recent send times: 481,840 sends across 105,326 senders at `train_end`. Two exact designs work. A per-sender sorted set keyed by `source_row` with the minute as score, counted with `ZCOUNT key (cutoff +inf` (the `(` makes the bound exclusive) and trimmed on each send. Or minute buckets: since timestamps have minute resolution, a hash of minute to count is exact and holds at most 1,440 fields even for the busiest sender (18,790 sends in that window).

**Distinct counterparties: one global edge set.** A directed edge (sender, receiver) is new for the sender's out-set exactly when it is new for the receiver's in-set, so one `SADD` result drives both `distinct_out` and `distinct_in`. Train and validation hold only **975,372 distinct pairs**. Encoding each edge as an integer from dense account ids and spreading them over 16,384 keys keeps every key in Redis's compact intset encoding, which uses "up to 10 times less memory" than the normal form ([Redis memory optimization](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/memory-optimization/)). The estimate is about 10-12 MB for edges and 20-30 MB for the 24-hour window. These are estimates from encoding rules, not measurements, and must be checked with `MEMORY USAGE`. Account ids should be assigned in the gold snapshot by first appearance in `(timestamp, source_row)` order, with new stream accounts getting the next id inside the script.

**One Redis Function per transaction does everything.** It takes the sender hash, receiver hash, edge shard and window key; checks both watermarks (a self-transfer touches one hash); returns the before-state; applies all updates; and writes the pending record. Redis Functions are the persisted, named form of scripts, so they survive a restart, unlike cached `EVALSHA` scripts ([Redis scripting](https://redis.io/docs/latest/develop/programmability/eval-intro/)). Because scores never feed back into state, a batch of calls can be pipelined in order and scored afterwards in one XGBoost call. Two settings protect the state. `maxmemory-policy noeviction` makes writes fail loudly instead of silently evicting a counter, which would reset a feature to zero ([Redis memory optimization](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/memory-optimization/)). And `maxmemory` needs real headroom, because a script that hits the limit after its first write can leave a partial update ([Redis scripting](https://redis.io/docs/latest/develop/programmability/eval-intro/)).

**Parity is proven row by row, not on averages.** Start from the `train_end` snapshot, replay all validation events through the online updater, and compare all nine features plus the in/out ratio with the batch output for the same `source_row`. Integers must match exactly and amounts exactly in micro-units; zero mismatches is the bar. Add a duplicate test (every event twice), a crash test, a tie test (shuffled same-minute arrivals) and a boundary test (a send exactly 24 hours earlier is excluded). A fast CI version can use a sample (the hub accounts plus 10,000 random accounts' full histories), with the full replay as a `slow` test. This is stricter than commercial feature platforms advertise. Tecton, Feast and Chalk all rely on time tiles merged at query time, which is exact only up to tile edges, and Tecton 1.0 changed its window's leading edge in a way its own docs warn can change served values ([Tecton](https://tecton-docs.pages.dev/docs/sdk-reference/feature-views/configuration/read-features/AggregationLeadingEdge), [Feast tiling](https://docs.feast.dev/getting-started/concepts/tiling)). The project's own ADR 0004 already found that Feast could not build these training features without leakage on same-minute ties.

## Rules, shadow mode and a plain consumer are what the industry actually runs

**Real fraud and AML stacks are hybrids.** Deterministic rules run next to an ML score, the outputs merge into alerts by a written policy, and a capacity-limited investigator queue feeds labels back. Dal Pozzolo's system diagram shows exactly these layers, and notes investigators "can only check few alerts per day", which is why precision@k at a daily capacity k is the operating metric ([TNNLS](https://boracchi.faculty.polimi.it/docs/2017_FraudsTNNLS.pdf)). Stripe Radar lets rules reference the ML risk score ([Stripe docs](https://docs.stripe.com/radar/rules)). Regulators do not ban ML: FATF says it can cut false positives, names explainability as the challenge, and keeps firms responsible for their models ([FATF](https://www.fatf-gafi.org/en/publications/Digitaltransformation/Opportunities-challenges-new-technologies-for-aml-cft.html)). The UK FCA's updated guide expects firms to measure the effectiveness of thresholds and to pilot new approaches ([FCA PS24/17](https://fca.org.uk/publication/policy/ps24-17.pdf)). Rule thresholds are tested "above and below the line": sampling just under a threshold shows what is missed, and checking above it shows what raising it would lose ([Deloitte](https://www2.deloitte.com/content/dam/Deloitte/de/Documents/finance/Deloitte-Optimizing-rule-based-transaction-monitoring-systems.pdf)). For AMLworld, simple rules that use only as-of state are velocity out of an account, fan-out and fan-in (many distinct receivers or senders in a window), structuring (several amounts just below a round threshold), and new account plus large amount; the existing "both accounts new → review" rule (FINDING-014) is a hard override. The combination policy belongs in an ADR: alert if any rule fires or the score passes a threshold, keep a `reasons[]` list of rule ids and top features on each alert, and fill k queue slots per simulated day. The payoff is a table reviewers trust: **rules-only, model-only and combined precision@k at the same k on validation**, plus what each catches that the other misses. Alerts leave through an outbox table written in the same Postgres transaction as the decision, so an alert can never exist without its decision, or the reverse.

**The industry tests in three stages: backtest, shadow, promote.** Stripe Radar shows how a rule would have acted on historical payments before it goes live ([Stripe docs](https://docs.stripe.com/radar/rules)). Uber runs candidate models in shadow, on identical live inputs with outputs logged but not acted on, for more than 75% of its critical online models, and backtests on production history to catch regressions "invisible in aggregate metrics" ([Uber Engineering](https://www.uber.com/gb/en/blog/raising-the-bar-on-ml-model-deployment-safety)). Sardine advises at least a week of shadow for new rules (vendor claim) ([Sardine](https://www.sardine.ai/blog/fraud-rules)). Kafka makes this cheap. The fast replay of validation is the backtest. A second consumer group on the same topic, writing to `decisions_shadow` and never to the alert queue, is shadow mode at almost no cost, because each group reads the log on its own. Champion/challenger (the live model against a candidate) is both groups scoring every event, with a job that reports agreement, alert overlap and, once labels arrive, precision@k per model, broken down by segment such as currency, payment format and cold-account class.

**A plain consumer beats a framework on this box.** Flink's shipped config sets the job manager to 1,600 MB and the task manager to 1,728 MB, about 3.3 GB before any Python worker ([Flink config.yaml](https://raw.githubusercontent.com/apache/flink/master/flink-dist/src/main/resources/config.yaml)). RisingWave wants at least 8 GiB per compute node ([RisingWave](https://docs.risingwave.com/deploy/hardware-requirements)). Bytewax is community-maintained since its company stopped in May 2025, with no release since November 2024 ([bytewax](https://github.com/bytewax/bytewax)). Quix Streams (3.28.1) is the one Python framework worth naming as the considered alternative. It fits in memory, but it keeps state in its own RocksDB, while the k3s scorer reads features from Redis, and its exactly-once covers Kafka outputs and its own state, not Redis or Postgres ([Quix configuration](https://quix.io/docs/quix-streams/configuration.html)). It would add a second copy of state without removing any of the hard parts. Flink is the streaming name job ads list most, but no source in this research measured that. The stronger interview story is "Flink's defaults alone exceed my budget, so I wrote a few hundred lines of consumer whose exactness is proven row by row, and I know where it stops scaling". Write that in an ADR with the numbers.

**Testing needs a real broker.** Unit tests mock only a thin wrapper around confluent-kafka. Integration tests run a real single-node KRaft broker; `apache/kafka-native` is acceptable here because CI is exactly the dev-and-test use Apache allows ([Docker Hub](https://hub.docker.com/r/apache/kafka-native)). How that broker runs inside a CI job that cannot reach other containers still has to be checked against the isolation probe. Fault tests, marked `slow`, kill the consumer at seeded points (including between the Redis update and the Postgres commit), restart the broker, and re-send slices. After each one, `count(*)` must equal `count(DISTINCT event_id)` and the number of events sent, the stored offset must equal the end of the topic, and Redis features must equal a batch recomputation.

## Recommended architecture and build order for this box

The flow is: `silver.transactions` (validation window only) → **replayer** (host job running as the reader identity, idempotent producer, pacing, seeded faults, checkpoint) → Kafka topic `transactions` (one partition) → **consumer** (k3s Deployment in the restricted `graphguard` namespace, micro-batches of 200-1,000 events, one Redis Function per event, XGBoost in process, rules) → Postgres `decisions` + `consumer_offsets` + `outbox` in one transaction → topics `alerts`, `decisions`, `transactions.dlq`; plus topic `labels` from the label simulator, and a shadow consumer group writing `decisions_shadow`. Postgres gets a new database and role through `pg_access.SERVICES`, so it is backed up automatically. A compose service would also work for the consumer, but a k3s Deployment reuses the scorer's restricted pod setup and network policy.

| Component | Cap (start) | Basis |
|---|---|---|
| Kafka 4.4.0 JVM broker, heap 256-384 MB | 768 MB | extrapolated from 300-400 MiB measured with a 1 GB heap; must be measured |
| Consumer (Python, librdkafka, XGBoost, rules) | ~400-512 MB | estimate; capped prefetch; must be measured |
| Shadow consumer (when running) | ~400 MB | same as consumer; run only during comparisons |
| Replayer (reads silver in batches, never all at once) | ~256-384 MB | estimate; lakehouse jobs peaked at 1.1-1.3 GB reading whole tables |
| `kafka_exporter` for lag | 32-64 MB | unmeasured guess |
| New Redis state (edges + 24h window + pending) | +30-45 MB inside the existing Redis cap | estimate from encoding rules |
| Postgres decisions DB | inside the existing Postgres cap | mostly disk: about 1M rows |

That is about **1.3-1.6 GB** with the shadow consumer stopped, and close to 2 GB with it running. It fits the 4 GB budget next to MLflow, Postgres, Redis, the lakehouse services and the scorer, but only if heavy lakehouse jobs and training do not run during a replay. Every number in the table is a starting cap to be replaced by a measured peak.

The build order below follows the project's one-step-at-a-time rule; each row can become a story with checkable acceptance criteria.

| # | Story | Done when |

| 2 | **Fix money seeding** (`sum()` → sequential; integer micro-units in batch and online) | snapshot equals batch `cum_sum` per account; features rebuilt; model retrained and republished, validation only |

## Conclusion

The main lesson is that "close to production" and "small" are not in conflict here. Production fraud streams earn trust through properties, not size: the same input always gives the same decision, repeats change nothing, labels come late and biased, and the model is always compared with rules and with a challenger. Every one of those properties can be shown on one partition of one broker, and a single-node system makes them easier to prove because the order is total. What the box cannot show is scale-out, and the honest move is to name the exact point where the design stops (one partition, receiver-side order) and the known way past it (a re-keyed second stage).

The research also changes the order of work. The riskiest part of Phase 6 is not Kafka at all; it is that the online features already disagree with training in two places. Fixing those, and proving parity offline before any broker exists, means that when Kafka arrives it only moves events that are already known to produce correct features. Kafka then becomes a transport to measure and harden, not a place where correctness bugs hide.
